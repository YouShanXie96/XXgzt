## Bug 1：图片全部没上传的直接原因

日志：
```
[fill-images] 1:1主图：按图位准备 1 张（1 张可上传）
[fill-images] 1:1主图异常："[object Object]" is not valid JSON（继续上传 3:4/详情/SKU）
[dialog-guard] 上架中断："[object Object]" is not valid JSON
```

**成因（代码级确定）**：v1.3.13 新增的限流检测脚本 `MEDIA_CHALLENGE_SCRIPT` 结尾是
`return {slider:slider,limited:limited};`（返回**对象**），而调用处写的是
`JSON.parse((await evalFrame(frame, MEDIA_CHALLENGE_SCRIPT)) || 'null')`。
`JSON.parse(对象)` 会先把对象转成字符串 `"[object Object]"`，于是抛
`"[object Object]" is not valid JSON`。这是第一张图上传循环里的第一次检测，
异常直接把 1:1 主图整段打断；后续透明素材图 / 3:4 / 详情 / SKU 图也都在这条链上，全部没有执行。

**修法**：
1. `MEDIA_CHALLENGE_SCRIPT` 改为 `return JSON.stringify({...})`；
2. `evalFrame()` 统一归一化：帧内脚本无论返回对象还是字符串，一律转成字符串，调用方都能 `JSON.parse`；
3. 新增模块级 `asJson(value)`，并把驱动内 75 处
   `JSON.parse((await win.webContents.executeJavaScript(...)) || 'null')`
   全部换成 `asJson(await ...)`。以后任何注入脚本返回对象都不会再打断整条上架流程。

## Bug 2：样品「未找到 · 控件态无法识别」

日志：
```
[fill-extra] ⚠ 正装仍未选中（页面「未找到」· 控件态无法识别）
```

**成因（代码级确定）**：`xhSampleRow()` 要求找到「文字规范化后**正好等于**"是否为样品"」的节点；
而同一份日志里的 `[field-diagnostic]` 明确显示，这一行实际渲染为
`"label":"是否为样品样品正装"` —— 标签和两个选项的文字连在一起，精确匹配永远失败，
于是 `xhSampleTargets()` 返回空数组。

**修法**：`xhSampleTargets()` 重写为结构无关算法：
1. 全文档扫文字**正好是**「正装」「样品」的叶子节点（不依赖任何 class 名）；
2. 取两两最近的公共祖先，作为这一组控件的容器（文字长度 ≤240 才算，避免抓整个表单）；
3. 容器内找 `input[type=radio]` / `[role=radio]`；没有 radio 就按 class 里的 `checked` 判定；
4. 点不准时返回坐标，主进程用 CDP 真实鼠标点击后再回读。

**验证方式（不是靠看代码猜）**：新增 `sample-locator-check.js`，用假 DOM 覆盖三种结构：
- A 原生 radio：正装 checked=true / 样品 checked=false → 通过
- B 纯 class 样式 radio（无 input）：正装 checked / 样品未选 → 通过
- C 文字粘连「是否为样品样品正装」：返回 0 个选项、不乱点 → 通过

**诊断增强**：仍找不到控件时，日志会带上现场
`{"docs":2,"正装文字":0,"样品文字":1,"radio":2,"命中":0}`。
下次一眼就能区分是「页面没渲染出这两个词」还是「定位没命中」，不需要再猜。
